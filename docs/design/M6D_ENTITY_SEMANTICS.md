Do not infer activation from a flag name: the only flag with that name is clear on the hero the operator was playing.

## 4. Question C — spatial representation

| Finding | Class |
|---|---|
| `ZSpatialEntity` (`0xA0` bytes): `m_mTransform` (`SMatrix43` at `0x20`) is **the cached object-to-world matrix** — `GetObjectToWorldMatrix()` returns `m_mTransform` after calling the engine's `ZSpatialEntity_UpdateCachedWorldMat` when `m_bWorldTransformDirty` is set; `m_vObjectToParentRotation` (`0x50`) / `m_vObjectToParentTranslation` (`0x60`) are the parent-relative transform; the bitfield at `0x6C` holds `m_bVisible`, `m_bParentHidden`, `m_bSceneChild`, `m_bIsDynamic`, `m_bForceVisible`, `m_bWorldTransformDirty`, `m_eRoomBehaviour`…; `m_eidParent` (`0x70`) and the intrusive transform tree `m_pTransformParent` / `m_pTransformChildren` / `m_pTransformNext` / `m_pTransformPrev` (`0x80`–`0x98`); `m_pTransformChangeCallBackEvent` (`0x18`). | [S] |
| What M6-B1/M6-C3 read is therefore the **cached world transform** plus its dirty bit, by field, with no call — on every read of both heroes the dirty bit was clear, so the cache was current. The local hero's value moved with gameplay (−83.84/14.75 in M6-B2, −83.74/14.70 in M6-C3, y by 4·10⁻⁵ across the restart), consistent with a live world position. | [R-C3] [R-prior] + [S] |
| Stored local (parent-relative) transform: `m_vObjectToParentTranslation` / `Rotation` — not yet read for either hero. 6. **Input and animation behaviour** — the `SGameInput` contract; not designed here.
7. **Game-world interactions** — not designed here.
8. **External multiplayer coordination** — not designed here; historical GNS stays excluded.

No generic entity-control API is proposed or authorized.

## 9. Remaining unknowns and risks

- The setting policy of `ENTITYFLAG_ACTIVATED` (which classes, when); the member and gate behind the hero's `m_bActive` property.
- The hero-spawn application: which system selects a spawn, how `m_nPlayerId` / `m_nSetId` / `m_sRepositoryId` take part, whether a hero can be placed by a spawn without a registry slot.
- The origin of z = −1.539 (physics placement vs template offset); whether Agent48's physics, animator and character core exist and run; whether it is drawn.
- The registry: what allocates a `ZNetPlayerController`, the slot lifetime across scene changes, whether `GetLocalPlayer` survives a second registered player (F1 says it would walk past the registry).
- `GetProperty`'s allocation through the engine's memory manager on the frame thread — benign for the upstream mods that use it every frame, unmeasured by this project.
- Risk of Option A: a `QueryInterface` or property walk on an entity whose type table differs from the SDK's model; mitigated as in M6-B1 by the typed index checks, per-field statuses and the fail-stop guard.

## 11. Stop

Not authorized by this record: installing or launching HITMAN; redeploying the Agent48 content; building or installing a Relay DLL; adding native observations; calling engine setters; changing transforms or character input; modifying player-registry slots; activating Agent48; enabling historical networking; multiplayer synchronization; M7–M9; declaring M6 complete. M6-C3 established a second engine entity; this record says what it most probably is — a complete but unspawned hero — and how to find out without touching it.
