## 4. Question C — spatial representation

| Finding | Class |

6. **Input and animation behaviour** — the `SGameInput` contract; not designed here.
7. **Game-world interactions** — not designed here.
8. **External multiplayer coordination** — not designed here; historical GNS stays excluded.

No generic entity-control API is proposed or authorized.

## 9. Remaining unknowns and risks

- The setting policy of `ENTITYFLAG_ACTIVATED` (which classes, when); the member and gate behind the hero's `m_bActive` property.
- The hero-spawn application: which system selects a spawn, how `m_nPlayerId` / `m_nSetId` / `m_sRepositoryId` take part, whether a hero can be placed by a spawn without a registry slot.
- The origin of z = −1.539 (physics placement vs template offset); whether Agent48's physics, animator and character core exist and run; whether it is drawn.
- The registry: what allocates a `ZNetPlayerController`, the slot lifetime across scene changes, whether `GetLocalPlayer` survives a second registered player (F1 says it would walk past the registry).
- `GetProperty`'s allocation through the engine's memory manager on the frame thread — benign for the upstream mods that use it every frame, unmeasured by this project.
- Risk of Option A: a `QueryInterface` or property walk on an entity whose type table differs from the SDK's model; mitigated as in M6-B1 by the typed index checks, per-field statuses and the fail-stop guard.
