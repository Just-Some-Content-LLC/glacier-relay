## 1. Executive technical conclusion

1. **A correction first.** The M5 closure text (section 36.6, written 2026-10-14) said the dormant Hitmen module had never been loaded by HITMAN. That was wrong: **experiment 4 loaded it once on 2026-10-06** under its own authorization, R1–R4 passed with 0 faults, and findings F1–F10 are the project's only runtime evidence about the player registry, the scene hooks and the brick list (corrected in `d955aaf`). Consequently **candidate A of this authorization has already been performed**; its evidence exists and is used here.
2. **What survived (capability 1 only, and only as files).** The historical second-Hitman method is content plus discovery: an SMF content mod adds `hitmen.brick` (one authored `agent47_default` hero `Agent48`, entity id `0xfeede715906f747f`, and a `herospawn` `Agent48Spawn` with `m_nPlayerId` 2) to global data as an external scene, and the mod finds that entity through the brick's blueprint factory each scene **(S)**. The content is not deployed on the operator's installation and never was during this project **(R4: `hitmen.brick loaded: false` on 4 checks; M0: no SMF deployment)**. Nothing about the engine instantiating, owning or animating a second hero on 3.280.0.0 is established **(U)**. The 2023 debug line "Found other hitman" is the only hint that the author ever saw one, on an unknown build **(A)**.
3. **The discovery mechanism exists in the current SDK by source** (`m_aLoadedBricks`, `ZEntityRef::GetBlueprintFactory`, `IEntityBlueprintFactory::GetSubEntityIndex` / `GetSubEntity`, `QueryInterface<ZHitman5>`) and is used by upstream mods **(S)**, but **no run of this project has executed it past the resource-id compare** — the brick was absent, so the historical loop never reached the factory cast **(R4 negative)**. Whether it resolves anything on this build is **U**.
4. **The historical method's local-player assumption conflicts with M5's observations in exactly the two-player case.** It resolves the local hero through `SDK()->GetLocalPlayer()`, which walks the SDK's `TArray` model of the registry at `0x390`; experiment 4 showed that model is wrong on this build (F1) and that the function returns the right entity only because slot 0 qualifies on its first iteration. With a second registered player that accident is the first thing to break. GlacierRelay never used that path; since M2 it reads inline slot 0 directly **(S, R5)**. The second finding of that kind: the historical code caches `ZEntityRef`s across frames until `ClearScene`; M5's accepted rule is to resolve on the applying frame and cache nothing, and the SDK declares entity deletion inside a scene **(S)**. Section 3.9.
5. **Identity.** A raw pointer is not identity: experiment 4 saw the same Hitman pointer values before and after a mission restart and could not tell a surviving object from a reused address (F7). The record offers a typed identity for authored entities — the owning brick's `ZRuntimeResourceID` plus `ZEntityType::m_nEntityID` — resolved afresh on every frame it is used, qualified by the attempt's generation (M5's mission generation) and by the entity's flags **(S)**; whether it holds at runtime is **U** until measured. Section 4.
6. **The smallest next experiment is a typed, read-only, journaled inspection in the M5 pattern (candidate B), not a repeat of candidate A.** Without content, it cannot observe a second entity — and says so — but it establishes, on the accepted command infrastructure and with the M5 gates, the three things every later stage stands on: the registry as it really is on this build (four slots typed, the three raw words at `0x390`), the brick list, and **a round-trip of the historical discovery mechanism against the one hero that exists** (the local hero's own brick and entity id resolved through the blueprint factory and compared with the registry's entity). It is falsifiable: if the round trip does not return the registry's entity, the historical method is broken on this build regardless of content. Sections 8–10.
7. **The first testable second-entity hypothesis** (capability 2) needs the content and is therefore not inert in the sense of this authorization: *"with `hitmen.brick` attached to global data on 3.280.0.0, the brick appears in the scene context's loaded bricks and entity `0xfeede715906f747f` resolves to a `ZHitman5` whose entity differs from the registry's local hero."* Its instrument is the candidate-B inspection with a `(brick, entity id)` parameter; its prerequisite is a content-deployment decision with its own restoration plan, because an SMF deployment changes game files outside the 26-file M0 hash set. Section 13 places it as M6-C, after M6-B.
8. **Primary architectural risk:** the local-player identity on which M2 telemetry gating, M5's mission generation and effectful gate, and every upstream mod rest is "registry slot 0"; the moment a second hero exists, the registry's real layout (unknown beyond slot 0's fields), the SDK's `GetLocalPlayer`, and the meaning of `m_bLocalPlayer` (already shown non-discriminating) are all unverified, so the project could lose its ability to say which hero is the controllable local player — before any question about the second one can be asked. Section 14.

### 3.9 Does the historical method rely on a lifecycle or registry assumption that conflicts with M5's observations?

Yes, in two places; compatible in three.

1. **Local-player resolution — conflict.** Historical: `SDK()->GetLocalPlayer()`; the SDK's loop over the `TArray` model. M5: slot 0 directly, because experiment 4 showed the model wrong (F1). With one player the two agree **(R4: slot 0's `hitman entity` equals the SDK's local player on all four dumps)**. With a second registered player, the SDK loop's correctness depends on `m_PlayerData.size()` and on which entry lacks `m_pNetPlayer` — values that experiment 4 showed are not what the model reads — so it may walk beyond the registry or return the wrong hero; and M5's "slot 0 is the local hero" is itself **A** for that case (slot 0 held player id 0 and `flags 0xA0` 0, slots 1–3 held −1 / `FFFFFFFF`; whether a second hero lands in slot 1 or displaces slot 0 is **U**). Everything that gates on the local hero (M2's attempt-gated telemetry, M5's generation, the effectful gate's `hero` tuple) inherits this.
2. **Cross-frame caching — conflict.** Historical: `m_OurHitman` and `m_OtherHitman` cached from discovery until `OnClearScene`. M5 (accepted): every engine handle resolved on the frame it is used, nothing cached across frames, the link generation re-read before a call. The SDK declares entity deletion inside a scene (`ZEntityManager_DeleteEntities`, `m_pDeletionListeners`, `ENTITYFLAG_PREDELETED`) **(S)**; experiment 4's pointer reuse across a restart (F7) shows why a cached reference is not evidence of a living object. An M6 observation must re-resolve per frame.
3. **Lifecycle keying — compatible.** Historical readiness = `m_pScene` ∧ `m_bSceneLoaded`, reset in `ClearScene`; this is the design experiment 4 found correct (F2: no `LoadScene` on restart) and the one M2–M5 use (plus stage 8 and scene type). One difference: the historical discovery also runs at the main menu (a local player resolves there, F5), so with the brick in global data a second hero could exist at the menu; M5's predicate treats the menu as "not playing", and `relay.inspect.outfit` is allowed there. An M6 inspection must be allowed at the menu and must not assume a mission.
4. **Thread — compatible.** Experiment 4 saw mod loading, both detours and the frame update on one thread; the M5 scheduler applies on the frame-update thread (the detour's thread). The same thread rule carries.
5. **Fault handling — compatible, M5 stricter.** Historical: a log-only SEH filter that never handles. M5: the same, plus a latch that disables the effectful path after any fault. An M6 inspection inherits the M5 guard.

A sixth point is not a conflict but a dependency the historical method never checked: it assumes the brick appears in `m_aLoadedBricks` of whatever scene is loaded because the global-data patch lists it as an external scene **(A)**. Experiment 4 saw 5 and 23 bricks without the content; whether a patched global data adds a 6th / 24th entry, in which scenes, and whether its root entity is instantiated before or after the scene reports loaded, is **U** and is the first thing M6-C would measure.

- **The local hero's identity fields:** `GetType()->m_nEntityID`, `m_nEntityFlags`, `m_nEntityPtrIndex`, the owning-chain depth to the closest blueprint-factory parent and that parent's brick id when it matches a list entry, `m_CharacterId`, `m_InitialOutfitId`, `m_bIsInvincible`, the outfit tuple (as M5), and the spatial read-outs: `m_mTransform.Trans` **raw** with `m_bWorldTransformDirty` and the `m_eRoomBehaviour` bits — **not** `GetObjectToWorldMatrix()`, which calls the engine's cache refresh when dirty; a stale-flagged position is reported as such.

## 6. BEAM / native responsibility boundary

Preserved from M5 (ADR 0002, 0009; section 36.3): **Glacier** owns physics, animation, NPC AI, collision, scripting and native entity lifetime; the **native adapter** owns bounded engine observations on the frame thread, entity-reference validation on the frame of use, and narrowly authorized engine operations behind a gate with a durable pre-call line and a fail-stop guard; **Elixir/OTP** owns session identities, command authority, external coordination, observation correlation, the journal and replay, and uncertainty and disconnect handling. M6 adds no BEAM responsibility for the engine's simulation: a second hero's animation, collision and perception stay Glacier's whatever drives its transform.

**Will high-frequency second-player movement need a different bounded data path?** By the numbers, yes, as a design question for a later stage. M5's control interface is one command per frame from a queue of 8, each command a ≤ 4,096-byte line with a validated UUID, a TTL of 100..10,000 ms and a mission-generation precondition, acknowledged with a result and journaled on BEAM in four to five entries **(S: `CommandProtocol.h`, the journal)**. The historical pose stream was 396 bytes at 30 Hz, unreliable, last-writer-wins **(S)**. A 30 Hz stream through the command path would be 30 journaled commands per second with request/response semantics that fit idempotent operations, not superseding state; the journal and the queue bounds are wrong for it by design, not by capacity. The shape that fits the division is a third kind of link beside telemetry (outbound observations) and commands (inbound operations): an inbound, versioned, bounded **state stream** — sequence-numbered samples of one declared actor's intent (a pose or a movement target), applied on the frame thread from a single latest-sample slot, rate-limited, superseded rather than queued, with the journal recording sessions, generations, rate statistics and refusals rather than samples, and every sample refused unless the actor's identity resolves on that frame. None of this is for M6-B or M6-C; capability (5) can be demonstrated through the existing command path (one transform set and its reversal), and the stream becomes a question only at (6).

## 9. Recommended next experiment — M6-B: `relay.inspect.players` v1 (read-only; proposed name)

One new allowlisted, read-only inspection, version 1, executed by the scheduler on the frame thread like `relay.inspect.outfit`, allowed at the main menu and in a mission, never on an idle frame, under the M5 fault guard, with the `[command] effectful` setting off and the applier not constructed. Parameters: optional `brick` (a 16-hex `ZRuntimeResourceID`) and optional `entity_id` (a 16-hex authored id); when absent they default to `[assembly:/_sdk/hitmen.brick].pc_entitytype` and `0xfeede715906f747f`, and the expected answer on an installation without the content is `found: false` — the negative control. It reports, each field with its status:

1. **Registry:** the three raw words at `0x390` (hex, and whether each is a slot address); the four slots' typed fields (section 5), with `hero_resolved` per slot.
2. **Bricks:** the count and up to 32 resource ids (hex); whether the named brick is present.
3. **Local hero identity:** from slot 0 (the M5 path, unchanged): `entity_id`, `entity_flags`, `entity_ptr_index`, the owning-chain depth, the closest blueprint-factory parent's brick id (matched against the list), `character_id`, `initial_outfit_id`, `invincible`, the outfit tuple, the raw transform (`x, y, z`, `transform_dirty`, `room_behaviour`).
4. **The round trip (the falsifiable step):** take the local hero's `(owning brick, entity_id)` from 3, run the historical lookup on that brick — type check of the factory, `GetSubEntityIndex(entity_id)`, `GetSubEntity` — and report `round_trip_index`, `round_trip_found`, and **`round_trip_same_entity`** (the resolved `GetEntity()` equals slot 0's). A `false` here, with the reads consistent, means the historical discovery mechanism does not resolve an authored hero through its brick on this build.
5. **The candidate:** `brick_present`, and when present the same lookup for `entity_id`: `found`, `index`, `hitman5_resolved`, `spatial_resolved`, `distinct_from_local` (entity pointers differ), and the candidate's identity fields and raw transform as in 3.

Bounds: the result line stays within 4,096 bytes and 48 observed entries; the registry alone is 4 × 11 fields, so the entry is **split into two commands with one implementation** (`relay.inspect.players` for the registry and bricks; `relay.inspect.entity` for the local hero, the round trip and the candidate) or the observed-entries bound is raised with BEAM's schema in step, as C-1 raised it from 16 to 48. The design records which; neither changes the protocol version.

Engine surface: inline reads of declared SDK memory; the virtual lookups on blueprint factories; **no engine function call** (the transform read is raw), no setter, no hook, no write, no caching across frames. New data imports: at most `Globals::ZTemplateEntityBlueprintFactory_vtbl`. The native and BEAM gates of M5 apply unchanged (clean build, 25/25 native runs, the raw import diff explained symbol by symbol, the C-2C probe matrix with a fake player source, 5 × the Elixir suite), and the run has its own authorization, pre-flight, dry run, operator checkpoint, cleanup and manifest as C-1b had.

What M6-B establishes: the registry as it really is on this build, typed and journaled; the brick list; the local hero's authored identity and owning brick; whether the historical lookup mechanism works on the one hero that exists; the negative control for the content. What it does not establish: anything about a second entity (2), its lifecycle (4) beyond the local hero's, or (5)–(8).

## 14. Primary architectural risk and the proposed authorization

**Primary architectural risk: the local-player identity.** Every accepted capability of the project — M2's attempt gating, M5's mission generation, the effectful gate's "hero wears A" precondition, and every upstream mod — identifies the controllable local player as "registry slot 0" (GlacierRelay) or as "the first `m_PlayerData` entry without a net player" (the SDK). The first holds on this build by observation of one player; the second by accident (F1). A second hero is precisely the condition under which neither is known to hold, the registry's real layout beyond slot 0 is unknown, and the one flag that names the local player is already known not to. If that identity becomes ambiguous, the project loses its ability to say which hero it is observing or commanding before it can ask anything about the second one. M6-B measures the registry as it is; M6-C's first abort condition is any change to the local-hero identity; and the identity rules of section 4 are designed so that the local hero is never identified by position alone once a second one exists (slot fields, entity id, owning brick and tuple together).

The main operational risk, distinct from the architectural one: a brick attached to global data may instantiate a hero at the main menu or during loading stages the frame update never sees (R4 F4), where no inspection can observe it and a fault would precede any evidence. M6-C's design must put the first observation at the earliest frame the scheduler runs and treat a boot or menu crash as its own finding.

**Smallest proposed inert runtime authorization (M6-B; not granted by this record):** implement and offline-validate the read-only inspection of section 9 (native and BEAM, in the C-1 pattern: no hook, no setter, no write, `[command] effectful` off, ≤ 1 new SDK data import, the M5 gates); then one attended HITMAN run on the observed build — main menu, Paris stationary, one restart, exit — issuing the inspection under the inert arming only, with the candidate defaulting to `hitmen.brick` / `0xfeede715906f747f` and expected absent; section 10 as the acceptance and abort matrix; the C-3 operator discipline (pre-flight, dry run against the frozen probe, operator checkpoint, install once, cleanup, manifest). No content deployment, no second entity, no transform or input write, no new hook.

### 16.4 Blueprint-factory discovery (the smallest supported read-only path)

The historical method's lookup (`m_aLoadedBricks` → the brick root's `GetBlueprintFactory()` → `GetSubEntityIndex(id)` → `GetSubEntity(root, index)`) is implemented as the SDK declares it, with each call a separately reviewable boundary: (1) brick ownership — the loaded-brick list's `m_RuntimeResourceID` / `m_EntityRef`, and an entity's `GetOwningEntity()` (the SDK's inline read of `m_nOwningEntityOffset`); (2) blueprint factory type checking — `GetBlueprintFactory()` null-checked, then `IsTemplateEntityBlueprintFactory()` (the SDK's vtable comparison against `Globals::ZTemplateEntityBlueprintFactory_vtbl`, the one new data import); (3) the authored entity id — `GetType()->m_nEntityID`; (4) sub-entity index lookup — `GetSubEntityIndex(id)`, a virtual call on the checked factory, −1 reported as such; (5) sub-entity resolution — `GetSubEntity(owner, index)`, null reported as such; (6) `ZHitman5` interface identification — the SDK's `QueryInterface`, exactly as M5 resolves the local hero. The local-hero round trip is falsifiable and its result distinguishes the six outcomes (`same_entity`, `different_entity`, `owner_unresolved`, `hero_not_representable`, `factory_unavailable`, `unsupported`); only a demonstrably valid lookup returning the wrong entity is the specific failure of the lookup contract, and one unavailable control never says that every blueprint-factory path is broken. The candidate lookup runs the same chain from the named brick's root and reports the candidate distinct from (or identical to) the local hero by pointer equality on that frame — an observation, never an identity.

### 16.5 The identity model (observational; not a proven stable identity)

An observed entity is described by an evidence tuple, never by a pointer: its owning brick (a runtime resource id, or the scene root), its authored entity id, the mission generation of the result (M5's edge-cached generation in the header, with the registry's own session id beside it in the players read-back), the frame, and its validity flags (`activated`, `predeleted`). Pointer equality is recorded only as an observation on one frame (`rt_same_entity`, `cand_distinct_from_local`); a reused pointer after a restart is never treated as proof that the same entity survived. M5's accepted local-hero identification (registry slot 0 → `ZHitman5`) is unchanged; the players inspection reads the same slot and reports the same kit id beside the registry's own outfit guid so a discrepancy between the two would be recorded, not resolved. Should a runtime observation contradict this model (a hero whose owning entity is neither a brick root nor the scene root; a round trip returning a different entity; a registry whose slot 0 is not the resolved hero), the record is the finding and the runtime scope stops there.

### 17.2 Correction A — blueprint-factory index bounds
