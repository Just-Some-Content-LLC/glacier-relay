## 3. SMF deployment analysis

Read from the framework's source at `main` `ec7806b4dd54cbfe015d08f8791d1a52aab8cdea` (2026-08-28; `src/deploy.ts` sha256 `357f9270…`, fetched 22:05Z; excerpts in `m6c1-research\smf-deploy-surface.txt`) and its `docs/` (S for the framework; A for the engine's reaction). Nothing of the framework is installed on this machine (search of the user profile and Program Files: none; the only related artefact is the SDK build's `quickentity-rs` cargo checkout).

**What a deploy does (S):**
1. For every mod in the load order, each `contentFolders` entry's `chunkN/` folders are processed: `*.entity.json` → TEMP/TBLU (+ `.meta`) through QuickEntity into `staging/chunkN/`; `*.entity.patch.json` → the target's **latest** TEMP/TBLU located in the game's packages with `rpkg-cli -hash_probe`, extracted, converted to QN, patched, converted back into `staging/chunkN/` (`docs/Special File Types.md`; `patchWorker.ts`). Raw files are copied as they are.
2. `staging/chunkN/` → `rpkg-cli -generate_rpkg_quickly_from` → **`chunkNpatch300.rpkg`**, copied into `Runtime` — or into the framework's own **`Output/`** folder when `config.outputToSeparateDirectory` is true (deploy.ts 2613–2617). A chunk folder containing a `chunkN.meta` would instead overwrite the base package (`docs/Folder Structure.md`) — not the case here.
3. `packagedefinition.txt`: the framework keeps `cleanPackageDefinition.txt` beside itself (copied from `Runtime` on first use, re-copied whenever the installed file does not contain `patchlevel=310`); decrypts it (`h6xtea.exe`), replaces **every** `patchlevel=N` by `patchlevel=310`, inserts each manifest `entity` entry's path on the line after the named partition's `@partition` line (the Hitmen entry under `@partition name=super`), appends four blank lines for the 8-byte block cipher, re-encrypts, and writes the result to `Runtime\packagedefinition.txt` (or `Output\`). The framework's own `cleanPackageDefinition.txt` at `main` decrypts to exactly the installation's current plaintext (sha256 `da70f1c9…`): the installation is unmodded by the framework's own test.
4. `Retail\thumbs.dat` is rewritten **only if** `config.skipIntro` is true or a mod declares `thumbs` entries (deploy.ts 2473: `Boot.entity` → `MainMenu.entity`; `[Hitman5]` additions). The Hitmen manifest has no `thumbs`; the SDK's SkipIntro mod is already enabled in the installation's `mods.ini`; **with `skipIntro: false` the thumbs stage is skipped and the file is untouched.**
5. No other game path is written (every `runtimePath` / `retailPath` write in deploy.ts is one of the above). The framework **never deletes** anything under `Runtime`: a `chunkNpatch300.rpkg` from an earlier deploy that the next deploy does not regenerate stays behind. Restoration is therefore the project's own mechanical step, never "deploy with no mods" (which would still write a package definition with every patch level at 310).
6. Cipher facts needed to verify the generated package definition read-only (S: public tool source, `h6xtea-xtea.go.txt`): a 16-byte constant header `223d6f9a b3f8feb6 61d9cc1c 62de8341`, a little-endian CRC32 of the plaintext, then XTEA (32 rounds, standard delta, little-endian 8-byte blocks) with the public key material; trailing NUL padding. The project's read-only decrypt reproduced the stored CRC on both files (`packagedefinition-partitions.txt`).

**The decrypted package definition (S, this installation):** 31 partitions in chunk order — `super` (chunk0, `parent=none`), `base`, `season3`, **`ancestral` (chunk3)**, `edgy`, `elegant`, `wet`, `trapped`, `legacy`, `season2`, `opulent`, `caged`, `greedy`, `salty`, `hawk` (chunk14), `theark`, `skunk`, `mongoose`, `colombia`, `miami`, `sheep`, `season1`, `hokkaido`, `colorado`, `bangkok`, `marrakesh`, `coastaltown`, **`paris` (chunk27, `parent=season1`)**, `dugong` (addon), `snug`, `golden` (chunk30); every `patchlevel=4` except `dugong`/`snug` 1 and `golden` 0 — which matches the `chunkNpatch1..4.rpkg` files on disk (the last update 2026-09-06 wrote the `patch4` files). The `paris` section lists `_Scene_FashionShowHit_01.entity` and `showstopper_story_content.brick`; the `super` section lists `Boot.entity`, `MainMenu.entity` and `vr_setup.brick`; no line mentions `_sdk`, `hitmen` or `globaldata`.

**Prerequisites of a deploy (S/A):** a framework release (the Mod Manager application with `Third-Party\rpkg-cli`, `quickentity-rs.exe`, `h6xtea.exe` — the visible `main` tree lists `h6xtea.exe` and `quickentity-rs.exe`; `rpkg-cli` is spawned by `rpkg.ts` and must ship with the release: **to be confirmed on the obtained release**); the game closed; `config.json` with `runtimePath`/`retailPath` pointing at the installation, `outputToSeparateDirectory: true`, `skipIntro: false`, `loadOrder` holding only the Hitmen mod; the mod folder (manifest + content folder) placed in the framework's `Mods` folder. With `outputToSeparateDirectory` true the installation is never written by the framework: the generated files land in `Output\` and the project installs and removes them with its own scripts, as it installs the DLL.

| Character guid | `cand_character_id` (authored `787c1ff2…`) | `hero_character_id` (zeros on this build, R6) | S / R6 |

**Rules.** (1) Simultaneous existence is claimed only when, on one frame, both tuples resolve and `cand_distinct_from_local` is true **and** the entity ids differ **and** the owning bricks differ **and** the character guids differ; pointer inequality alone (`cand_distinct_from_local` is pointer-based) is an observation, not identity. (2) Across frames the candidate is re-resolved by `(brick, id)` on every inspection; equality of the tuple's authored elements is identity, equality of a pointer is not recorded as such (the inspection reports no pointer). (3) Across a restart the generation changes; the same authored elements under the new generation are "the same authored entity in the new attempt"; nothing about object survival is inferred (the M6-B2 rule). (4) Invalidation: `ClearScene` fires on a restart (flag true) and on the exit to the menu (R4); the inspection runs only on frames with a loaded scene and never caches a reference, so a reference cannot outlive its frame; an inspection issued during the fall or the reload answers with `cand_brick_present` false or `unavailable` reasons — that answer is the lifetime evidence, never a stale value. (5) `m_bLocalPlayer` is never used (R4, R6). (6) No cross-frame caching of raw entity pointers is proposed anywhere; the historical module's `m_OtherHitman` caching is explicitly not carried.

**Registry membership** of Agent48 (the `herospawn`'s player id 2) is a separate question: the accepted `relay.inspect.players` reports per slot whether an entity and a hero resolve, the player id, the flags word and the session, and for slot 0 the kit id and outfit guid; it does not report a slot's entity id or character guid, so a populated slot 1–3 could be observed but not tied to Agent48 by authored identity (6.3 names the read-only extension that would).
