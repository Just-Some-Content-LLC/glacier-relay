### 2.2 Answers

1. **What a `disguise.equipped` repository id identifies.** The `ZRepositoryID` of an **outfit definition** — the global outfit kit entity (`ZGlobalOutfitKit::m_sId`) in the loaded global data — not an instance, not a charset or variation. Chain of evidence: the engine passes the id as the reflection type `ZRepositoryID` (M2 §34); the Relay's `contract.started.starting_disguise_repository_id` and the attempt's `disguise.equipped (initial)` id are the same text (`874c4c48…` in every Paris run); the engine's own code compares a kit's `m_sId` to the contract's `m_StartupDisguiseId` and keys its kit map by the same type (Randomizer); the cloth-bundle hook takes the repository id as the outfit's identity. **Not runtime-confirmed through Relay:** that `ZHitman5::m_rOutfitKit->m_sId` equals the id of the last `Disguise` telemetry after a change; an inert read-back (section 11, stage C-1) can confirm it.
2. **Is the id sufficient to resolve a usable `ZGlobalOutfitKit`?** Sufficient to *look up*: `Globals::ContentKitManager->m_repositoryGlobalOutfitKits.find(id)` returns the kit's `TEntityRef` when the kit is in the currently loaded global data. Usable only after validation on the applying frame: the entry exists; `TEntityRef::operator bool` (entity ref and interface pointer non-null); `m_aCharSets.size() > charset`; the collection pointer non-null; `m_aCharacters[ECSCT_HeroA]` non-null; `m_aVariations.size() > variation`. A kit absent from the map (season brick not loaded) is `precondition_failed` (not resolvable), never an error. Caveat: `TMap::find` walks the engine's tree with the SDK's `ZGuid::operator<`; the Randomizer relies on it in production, but a linear scan with `operator==` over the map (hundreds of entries, once per command) is the fallback that cannot disagree with the engine's ordering.
3. **Kit data that can be enumerated safely.** On the frame thread, read-only: the map's size and each entry's `m_sId`, `m_sCommonName`, `m_bIsHitmanSuit`, `m_bHeroDisguiseAvailable`, `m_eActorType`, `m_eOutfitType`, `m_aCharSets.size()` and, per charset, the HeroA variation count. Nothing is written; the `m_Outfit` resource ids are not touched. These reads are the proposed `relay.inspect.outfit` read-back (section 11).
4. **Player types usable without resource-table mutation.** Only `ECSCT_HeroA`. The Player mod's "Actor" and "Nude" paths exist precisely because the hero can only wear the HeroA variations; they mutate the shared kit's HeroA resource ids and restore them afterwards. M5-C fixes the character type to HeroA and refuses kits whose selected charset has no HeroA collection or zero HeroA variations.
5. **Charset and variation.** `nCharset` indexes `m_aCharSets`; `nVariation` indexes `m_aCharSets[nCharset]->m_aCharacters[HeroA]->m_aVariations`. The engine's current tuple is `ZHitman5::m_nOutfitCharset / m_nOutfitVariation` beside `m_rOutfitKit`. The Player mod resets both to 0 on a kit change. M5-C v1 takes **no** charset/variation parameter: charset 0, variation 0, validated against the kit's sizes (the observed hero suit is charset 0 / variation 0 in the Player mod's seeding; to be read back in C-1). The reversal uses the saved prior tuple exactly.
6. **Reselecting an existing kit without allocating or mutating shared resources.** From the adapter's side, yes: with HeroA no kit data is written, the kit reference is read from the engine's map and passed by value. Inside the engine `SetOutfit` streams the outfit's resources and creates a cloth bundle (the hook above shows the path); that allocation is the engine's own, happens on every gameplay disguise change, and is outside the adapter's control. The flags are passed as the Player mod does (`bEnableOutfitModifiers=false`, `bIgnoreOutifChange=false`); **`bIgnoreOutifChange`'s semantics are not established by source** (plausibly "do not run the outfit-change reactions"); M5-C uses the Player mod's values, documented as such.
7. **Evidence that a kit reference remains valid for the applying frame.** The kit is an entity of a global-data brick that stays loaded for the scene; the Player mod keeps a `TEntityRef` across frames in production use, and the Outfits mod unloads bricks only at scene clear/start. That is precedent, not proof. The contract therefore is: resolve the kit on the applying frame, validate it, call `SetOutfit` in the same function, never store the reference; a kit resolved and used within one frame cannot outlive a brick unload that happens on a scene transition, which the precondition excludes.
8. **Functions and globals to resolve and check.** `Functions::ZHitman5_SetOutfit->Exists()` before every use (the SDK resolves the pattern at startup inside `ZHMModSDK.dll`; the adapter imports the static; a 14-byte wildcard-free pattern is brittle across builds and must be reported in the inert read-back as `set_outfit_available`). Null-checked globals (not `EngineFunction`s): `Globals::ContentKitManager`, `Globals::PlayerRegistry` (already used), `Globals::Hitman5Module`, `Globals::ApplicationEngineWin32` (already used), optionally `Globals::ContractsManager` for the startup-disguise cross-check. The hero: the adapter must **not** use `SDK()->GetLocalPlayer()` as is — it walks the SDK's `TArray` model of the registry at 0x390, which the adapter's own archaeology found unreliable (`SceneObservation.cpp:35–37`); the adapter reads inline slot 0 and would take `m_aPlayerData[0].m_Controller.m_HitmanEntity`, construct `TEntityRef<ZHitman5>` (a `QueryInterface` through the type registry), and require `operator bool` plus a readable `m_rOutfitKit` before use.
9. **Unsupported or uncertain.** Non-HeroA character types (excluded); kits outside the loaded bricks (refused); `bIgnoreOutifChange` semantics (unknown); whether `ZHitman5_SetOutfit` emits the engine's `Disguise` telemetry (unknown, section 6); the hero entity's validity during streaming and transitions (the precondition excludes transitions; validity on the applying frame is checked, not proven); multiplayer slots (slot 0 only, single player only); the thread the engine expects `SetOutfit` on — the Player mod calls it from the UI draw and the Randomizer from inside the engine's own call; the adapter would call it from the frame update, which M5-B showed is the engine's main thread on this build (section 4 keeps that an observation, not a guarantee).

No repository id is treated as interchangeable with a kit reference: the wire carries the id (a UUID string, as today's reserved schema), the adapter resolves it per frame, and no pointer, entity reference, resource id or address ever becomes a protocol field (ADR 0001, ADR 0009).

## 3. Fresh mission-generation validation proposal (research section 4)

### 3.1 The race, restated as a requirement

Live findings (M5 §19.6): attempt 1 had session `…a105ec5f…`; `contract.ended` (restart) was published at 01:49:56.704 with that id; the registry slot already held `…30ccebb9…` on the fall-edge frame at 01:49:57.628 (`mission.stopped` carried it); the native edge-cached generation stayed `…a105ec5f…` until the fall (≈0.92 s); the next attempt rose with `…30ccebb9…` 11.1 s later (`contract.started` 23 ms after the rise); the scene resource was identical. **The edge-cached generation alone is not a precondition.**

### 3.2 The frame-validated contract (`MissionPrecondition`, evaluated on the applying frame, fail-closed)

| Field | Source | Rule |
|---|---|---|
| `expected_generation` | the command (BEAM's view: the contract session id of the open attempt, from `contract.started`/`mission.playing`) | must be present for an effectful entry (schema `preconditions: [:mission_generation]` already) |
| `generation_at_receipt` | the native link thread at receipt, copied from the value the frame thread last published under the queue mutex (never an engine read on the network thread) | recorded in the result; must equal `expected_generation`, else `precondition_failed (receipt generation)` |
| `generation_fresh` | the registry slot-0 session id **read on the applying frame** (`SceneObservation::ObserveGameSessionId`, same guards: non-empty, ≤ 256 bytes, non-null buffer) | must be present and equal to both of the above, else `precondition_failed (fresh generation)` / `unavailable (registry)` |
| `mission_playing`, stable | `MissionObserver::IsMissionPlaying` on this frame's `SceneState` (scene type `mission`, loading stage 8, `scene_loaded`) **and** the rise at least 1,000 ms and 60 frames ago **and** a `contract.started` for `generation_fresh` already normalized by the adapter | the restart showed `contract.ended` 0.9 s before the fall and `contract.started` 23 ms after the rise; "stable" excludes both windows |
| `scene` | this frame's `SceneState`: `available`, `scene_loaded`, `loading_stage == 8`, `scene_type == "mission"`, the scene resource equal to the one recorded at the rise | any difference → `precondition_failed (scene)` |
| `local_player` | slot-0 `m_HitmanEntity` → `TEntityRef<ZHitman5>` valid, `m_rOutfitKit` valid, the hero's `m_InitialOutfitId`/current kit readable | invalid → `unavailable (player)` |
| `no_transition` | the adapter's transition epoch (3.3) unchanged between receipt and apply, **and** no `contract.ended` normalized for the current generation since the rise, **and** the predicate true on the previous frame too | changed → `precondition_failed (transition)` |
| `target_state` (command-specific) | for the outfit entry: the kit resolvable and HeroA-usable (section 2), `expect_current` (when given) equal to the hero's current kit `m_sId` | mismatch → `precondition_failed (target)` |

Any required field unavailable → `unavailable` with the field named; any mismatch → `precondition_failed` with the field named; never a partial apply. The result carries all three generations and the epoch so BEAM and the journal show exactly which comparison decided.

### 3.3 A Relay-authored transition epoch

Proposal: `transition_epoch`, a `uint64` owned by the plugin and published to the command path with the generation under the mutex. It advances on evidence only: every mission-predicate edge (rise and fall), every `contract.ended` the normalizer attributes to the current attempt, every observed change of the registry session id on a frame it is read (edge frames today; apply frames with this proposal), and every `scene_loaded` false observed while the predicate holds. It is **not** an engine epoch and must be labelled `relay_transition_epoch` everywhere; it adds safety because it detects a transition that began between receipt and apply even when the session id happens to be unchanged (the "same session, entities replaced" case the M5-B record left unobserved). It does not detect what no evidence shows; in the observed restart it would have advanced at `contract.ended` (0.9 s before the fall), which is exactly the window the cached generation missed.

### 3.4 Frame-local registry read versus the edge-only strategy

Today the registry string is read only on edge frames (M2 Stage A), to avoid touching the registry every frame. Reading it on every frame costs one bounded string copy and compare (negligible against the frame budget) but widens exposure to a torn read: `ZString` is a size and a pointer; the engine's replication code (`ZPlayerRegistry` is a `ZBaseReplica`) may reassign it on another thread, so a read racing a reassignment could see a size with a stale pointer. The adapter's existing guards (size bounds, null check, bounded copy inside `RelayLog::Guard`'s SEH wrapper) are the same for every read. Recommendation: read on **apply frames** (one read per command, under the same guards, and read twice with the two copies required to be equal) and keep the edge reads; do not read on idle frames. Lifetime risk is bounded to the apply frame, the same frame the engine call itself is made on. The restart evidence shows the registry changes while the predicate still holds, so the fresh read is what catches the race; the twice-read rule and the epoch catch the torn-read case by failing closed.

No new live run was performed; the proposal is checked against the M5 §19 recording and the M4 and M2 restart/exit timelines only.

## 4. Native thread and lifetime constraints (research section 5)

Preserved as hard rules for any M5-C change: the network thread performs no engine access (it copies published values under the mutex and never dereferences engine objects); the scheduler applies at most one command per frame; every engine object (hero, kit, registry string, scene context) is resolved fresh on the applying frame and used within the same call; every `EngineFunction` is checked with `Exists()` and every global null-checked before use; no engine object is cached across frames or mission transitions; no command is applied while a transition is detected (section 3); no pointer, address, entity reference or resource id crosses the wire.

Additional synchronization identified:

1. **Link generation versus apply.** The scheduler already drops a command whose link generation is not the current one. For an effectful entry it must re-read `LinkGeneration()` immediately before the engine call and refuse if it changed; the remaining window is microseconds and cannot be closed from the frame thread, so a result produced after a link loss is lost and BEAM keeps the command `unknown` — the operator then re-observes (inert read-back) before any reversal.
2. **Epoch and generation snapshot at receipt.** The network thread must snapshot `generation_at_receipt` and `epoch_at_receipt` from the frame thread's published copy inside the same mutex acquisition that enqueues the command, so the two cannot interleave with a frame-thread update.
3. **One effectful command per arming.** BEAM's authority stays one-in-flight; the native queue keeps capacity 8, but an effectful entry is additionally refused as `busy` if any other effectful command is queued (the first inert design never had two effects pending).
4. **Fault containment.** `RelayLog::Guard` (SEH `__try/__except` with `LogFault`) already wraps the frame update; the apply call gets its own guard scope so a fault inside `SetOutfit` is logged with the command id and surfaces as `failed (fault)` rather than taking the frame down — with the explicit caveat that a fault inside the engine may leave engine state inconsistent, which is a stop condition for the run, not something the adapter can repair.

The M5-B thread relationship (detour, frame update and scheduler on one engine thread) holds for HITMAN 3.280.0.0 with SDK 4.1.1 on one run; it is an observation to re-verify in every runtime experiment's log, not a property of every game version.

## 5. Peer trust decision and residual risks (research section 6)

The facts: loopback is a network boundary, not process authentication; the adapter's instance id is a claim; the operator's arming authenticates the operator's intent, not the peer; the same id on the telemetry and command links shows both claim one instance, not that either is HITMAN; and any local process with access to the command authority can issue commands without remote exposure. BEAM runs in WSL2 and sees every Windows client through the localhost forwarding (the peer address `127.0.0.1:45140` in §19 is the forwarder's, not HITMAN's ephemeral port), so no socket-level peer credential (SO_PEERCRED, named-pipe client PID) is available across that boundary.

| Mechanism | What it proves | What it does not prove | Cost / fit |
|---|---|---|---|
| **Run-scoped shared token**: `install.sh` writes a random 32-byte token into `mods/GlacierRelay.ini` (`[command] token`) and BEAM receives the same token in its environment at start; the hello carries an HMAC over the welcome's nonce and link generation with that token (BEAM sends the nonce in the welcome; a second hello line answers it) | the connecting process could read the token placed for this run — it ran as the operator's Windows user, on this machine, during the install window | that the process is HITMAN or that the code is our DLL; any process of the same user can read `retail/mods/` | small protocol addition (one nonce field, one answer line); the token is removed with the ini at cleanup; a real mechanism, honestly named "possession of the run token" |
| **Telemetry corroboration**: the hello's `adapter_instance_id` equals the identified telemetry connection's; results' frame numbers increase monotonically and their scene read-backs agree with the telemetry attempt state | both links present one instance and the peer sees the same scene the observer sees | origin: the native log prints the id and any local process could replay it | already available (M5-B shows it: `78f4b136…` on both links); zero cost; corroboration only |
| **OS socket-ownership check** (operator tooling, out of band): at arm time `Get-NetTCPConnection -RemotePort 4749 -State Established` on Windows lists the owning process of every client of 4749; require exactly one, `HITMAN3.exe`, and BEAM to hold exactly one link | the Windows kernel's statement that the sole client of the command port is the HITMAN process at that instant | that the code inside HITMAN is ours (another loaded mod in the same process could connect; `mods.ini` enables `editor`, `freecam`, `skipintro`, `nopause` beside ours) | one command in `cmd.exs`'s arm path; recorded in evidence; strong against out-of-process impostors |
| **Operator-in-the-loop research mode**: one-shot arming (arm → exactly one effectful command → automatic disarm) with an arming TTL (30 s), the operator watching the game | operator intent and a bounded window | peer identity | BEAM-only change; narrows the exposure to seconds |
| Cryptographic peer authentication (certificates, a signed native build attesting itself) | process-independent identity | not available: the DLL has no key store, the SDK no attestation, and a key in the DLL is readable by the same local processes | not fit for this stage |

**Recommendation:** controlled local operation, labelled accurately: `trust.peer = :identified`, `trust.authenticated = false` **unless** the run token is implemented, in which case a new state `:token_verified` ("verified possession of the run token; not process identity") — never `:authenticated`. The first effectful experiment requires all of: the run token verified, telemetry corroboration true, the OS socket-ownership check recorded at arm time, one-shot arming with a TTL, and the operator present. The schema's `trust: :authenticated` requirement on `player.outfit.set` is to be re-decided by the operator: either it stays (and M5-C cannot proceed without a real authentication mechanism, which this environment does not offer) or it becomes `:token_verified` with the residual risk below accepted for the research run.

**Residual risk (stated, not minimized):** during the minutes between install and cleanup, any process running as the operator's Windows user on this single-user machine, with access to `retail/mods/GlacierRelay.ini` and the loopback, could present the token and, if the operator arms in that window, issue the one allowed command; any code inside the HITMAN process could do the same without the token check mattering. The design accepts this only for an operator-attended research run whose single effect is a reversible outfit change in a non-hostile context, and records every arming with the corroboration evidence.

## 6. Command-effect and reversal analysis (research section 7)

**The exit criterion** ("one safe, reversible semantic command changes observable game state", refined in M5 §13 to require `observed` for both the effect and the reversal, through engine-authored evidence where the vocabulary carries it, otherwise through the native read-back labelled as such).

**Native value restoration** is achievable: before the write the apply path reads the hero's `m_rOutfitKit->m_sId`, `m_nOutfitCharset`, `m_nOutfitVariation` (the prior tuple, returned in the result as `observed.previous`); the reversal is a second `player.outfit.set` with the prior id (and the prior charset/variation once v1 carries them), re-resolving the kit by id on its own applying frame. Reversal is its own command with its own ladder; nothing auto-reverts (M5 §9).

**Gameplay consequence restoration is not guaranteed and cannot be claimed.** The engine's disguise logic reacts to outfit changes: trespass and suspicion are evaluated against the worn outfit's category (`m_eOutfitAICategory`, `m_bAuthorityFigure`, `m_bWeaponsAllowed`); NPCs who witness a change react; the B3 model recorded that a change *clears* a compromise (M2 §36: "change-time clear"), so switching away and back can clear an engine-side compromised state that was present before — a consequence the reversal does not undo. Script state (missions that key on the current disguise) is unobservable. The experiment must therefore record "residual gameplay consequences unknown" as a standing outcome, never "fully reversed".

**Smallest safe test context.** The Paris starting position in the hitman suit, before any interaction, standing still, no trespass, no illegal item — the state every recorded run began in (`disguise.equipped (initial) 874c4c48…`). Target: **another hitman suit** (a kit with `m_bIsHitmanSuit == true` and a different `m_sId`), so the AI category does not change (suit → suit), minimizing NPC reaction and script interaction while still being a distinct outfit definition with a distinct repository id (the vocabulary distinguishes it). Whether suit-to-suit is "observable game state" in the operator's sense is a visible model change; the Relay's vocabulary would carry it only if the engine emits `Disguise` for it. An isolated non-hostile environment (training facility) would narrow NPC consequences further but changes the established route and the accepted baselines; recommended only if the Paris start proves noisy.

**Does `ZHitman5_SetOutfit` emit the engine's `Disguise` telemetry? Unknown by source.** Evidence points: the engine calls `SetOutfit` itself for the startup disguise (the Randomizer intercepts exactly that call), yet the `StartingSuit` telemetry arrives seconds later (3.4 s and 7.0 s after the rise in §19; 27.7 s in M4), from game logic above the setter; the B3 `Disguise` changes came from gameplay disguise actions whose call chain (action → setter → telemetry, or action → telemetry) is not visible in the SDK. A direct `SetOutfit` may change the outfit without any `Disguise` event. The design must work either way; if no engine-authored event follows, the only independent observations available are a **later-frame native re-observation** (`relay.inspect.outfit` on a different frame reporting the hero's current tuple — native, labelled as such), and the **operator's visual confirmation** recorded through the operator API as `observed_operator` — neither is engine-authored.

| command accepted | BEAM authority | `accepted` |
| applied by the native API | native frame thread: `SetOutfit` returned without fault after the preconditions held | `applied` (the engine took the call; nothing more) |
| native outfit tuple read back | native, same frame after the call: `m_rOutfitKit->m_sId`, charset, variation | `observed: :native` (`observed.current`), never independent |
| engine-authored disguise event observed | BEAM: a `disguise.equipped (change)` correlated per section 7 | `observed: :engine_consistent` (consistent with the command; attribution not provable) |
| visibly confirmed outfit change | the operator, through the operator API with a free-text note | `observed: :operator` |
| reversal requested | BEAM: a second command with the prior id | its own ladder |
| original tuple restored | native read-back of the reversal equal to `observed.previous` of the first command | `restored: :native` |
| independent observation of reversal | engine event / operator, as above | `restored: :engine_consistent` / `:operator` |
| residual gameplay consequences | nobody can establish them | `consequences: :unknown` (always) |

**If outfit reversibility cannot be justified**, the time-scale alternative (`Globals::GameTimeManager->m_fGameTimeMultiplier`, a float field the World mod writes every frame, `ZGameTime.h:101`, `World.cpp:67–71`) offers exact native restoration and no AI-category semantics, but it is a direct field write with no engine API, no vocabulary event, and a global effect on every simulation (AI timers, animations, scripted delays) while active; its only independent observation is indirect (the ratio of `engine_timestamp_s` deltas to wall-clock deltas across two later telemetry events) and the operator's perception. It is the fallback, not the preferred candidate (section 9).

## 7. Status and observation policy (research section 8)

The ladder stays: `accepted` (BEAM) → `transmitted` → `received` (native link thread) → terminal on the frame (`applied` / `failed` / `rejected` / `expired` / `precondition_failed` / `unavailable`, or `busy` / `duplicate` from the link thread) → `observed` (BEAM, from evidence it holds) → `unknown` after an ambiguous loss. A native reply — fake or real — is never promoted to an independent observation by assertion: `observed: :native` means "the peer says so".

**Correlating a `disguise.equipped` with a command** (the engine, a script or the operator can cause the same event): BEAM records `observed: :engine_consistent` for command C only when all hold — the envelope's `adapter_instance_id` equals the link's hello id and the telemetry connection's identified id; its `contract_session_id` equals C's `generation_fresh`; its `disguise_repository_id` equals C's requested id; its `kind` is `change`; its native timestamp is after C's result `native_at` and within a bounded window (proposed 5,000 ms, measured against the engine's own disguise-change latency in C-3); its sequence is greater than the last sequence BEAM had received when C was accepted; no other outfit command of this link was in flight or applied inside the window; and the operator has not recorded a manual disguise change in the window. If any condition fails the event is reported as `unrelated` or `ambiguous` (two possible causes), never attributed. The report wording is "consistent with command C", never "caused by".

## 8. Late expired result policy (research section 9)

Current policy (unchanged in this research): a terminal timeout marks the command `unknown (terminal_timeout)`; a later result for it is journaled as `anomaly.late_result` and the command's history is not rewritten (M5 §18.7 observed this against the probe with a 2 s fake frame).

Analysis: native's `expired` is produced by the scheduler **before** any dispatch, after `MarkDone(Expired)` in the dedup ring, so an `expired` result from the same adapter instance and the same link generation with the exact command id is the native side's statement that the command was never applied, and a re-send of the same id is answered `duplicate` (done) without execution while the ring entry exists. The ring entry is a bounded cache (64 ids); it is not what proves non-execution — the late terminal itself is, provided: the link generation matches the command's (a reconnect clears the queue and such a command has no result at all); the adapter instance matches the hello's; the id matches exactly; the status is one that asserts non-application (`expired`, `rejected`, `precondition_failed`, `unavailable`) — a late `applied` must never refine anything (it would assert an effect without the frame evidence BEAM expected); it is the first terminal for the id; and no later terminal contradicts it (a second terminal → `conflicting`, both kept).

Proposed future change (separate, BEAM-only, after M5-C review; not made now): on such a late non-application terminal, append `command.unknown_refined` to the journal and set `resolution: %{native_terminal: "expired", late_by_ms: …}` on the command while `status` **stays `unknown`**; status text reads "unknown; native later reported expired (not applied)". No automatic retry, no rewrite of earlier entries, no refinement from a reconnected link or a different instance. Justified because the first effectful command's operator must know whether an `unknown` could have been applied before deciding on a reversal; it is small and purely additive.
