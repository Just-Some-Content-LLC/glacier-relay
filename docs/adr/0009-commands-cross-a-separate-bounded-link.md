# ADR 0009 — Commands cross a separate, native-initiated, bounded command link; the observer path is never the command path

**Status:** Proposed (2026-10-13, with the M5 design investigation `docs/design/M5_COMMAND_CHANNEL.md`). Scope: **M5 — Command channel only.** Nothing here authorizes implementation, a native change, a DLL, a runtime experiment, browser controls, spatial work or M6–M9; each M5 stage needs its own review and authorization.

## Context

M4 closed an evidence-preserving observer: Glacier → native adapter → versioned envelopes over a one-way loopback TCP client → wire validation → `MissionSession` / `Session.Fold` → recorder → verified reader → replay → report → statistics. Its integrity rests on facts that are enforced today: the native side only connects out and discards inbound bytes (ADR 0005; `TcpRelaySink`), BEAM never writes to the socket (tested), the dashboard is read-only with no path to the wire (ADR 0007), recordings are append-only and replay never opens a socket (ADR 0008), and the adapter performs no engine write. ADR 0003 names commands as the opposite direction of the same versioned semantic protocol; ADRs 0006–0008 each state they do not open that direction.

The SDK evidence (M5 design, section 1.2) shows that every engine function and global is pattern-scanned and silently absent on another build, that entity references do not track lifetime, that the frame update is the only place the adapter touches the engine, and that the repository's one existing inbound socket (the Editor mod) mutates engine state on its socket thread — the anti-pattern. The 2023 Hitmen experiment wrote untrusted bytes into engine memory by array index over an unversioned unreliable transport; its archaeology's verdict ("semantic versioned messages; networking belongs to BEAM") stands.

## Decision

1. **A separate link, native-initiated, explicitly duplex, loopback only.** Commands and their results travel on a second TCP connection that the native adapter opens as a client to a second BEAM listener (`127.0.0.1:4749`), only when the native setting `[command] enabled = true` (default `false`) and the BEAM flag `GLACIER_RELAY_COMMAND=1` (default off) are both set. The telemetry connection stays one-way and best-effort and is not modified; the native side still never listens.
2. **A compiled allowlist and a versioned command protocol.** A command is `{command_protocol_version, kind, command_id, issued_at, ttl_ms, name, version, params}` with strictly typed, bounded parameters per `(name, version)`; a result is `{…, adapter_instance_id, status, reason, native_at, frame, observed}`. Unknown kinds, names, versions or malformed lines are rejected with a result or close the link; nothing is ever applied by default. There is no generic function call, property setter, script or memory write; no pointer, offset, vtable or entity reference crosses the link (ADR 0001).
3. **Engine writes happen only on the applying frame, through SDK wrappers, after fresh resolution and `Exists()` checks.** The link thread parses, validates, deduplicates and queues; the frame update applies at most one command per frame after re-checking TTL and preconditions against that frame's scene and mission state, reads the targeted state before and after, and queues the result. A lost link clears the queue; nothing pending is applied afterwards.
4. **One armed BEAM authority issues and journals.** `GlacierRelay.Command.Authority`, in an optional subtree, is the only issuer; it refuses while disarmed (arming is an operator action per session, undone by disarm or link loss), allows one command in flight, never reuses a `command_id`, never retries an `unknown` command automatically, and appends every transition to an append-only journal separate from the recordings.
5. **Applied is not observed.** The status ladder separates accepted, transmitted, received, applied (or a terminal rejection) and observed; `observed` is established by BEAM from evidence the observer already holds (an engine-authored Relay event correlated by instance, time and content) or, where the vocabulary carries no such event, by the native read-back labelled `observed_native`. A transport acknowledgement is never confirmation. No exactly-once execution is claimed: at most once per `command_id` per native instance, with `unknown` as an honest outcome.
6. **Every effectful command names its reversal**, and the milestone's success requires both the effect and the reversal to reach `observed`; the system never auto-reverts.
7. **The observer path is never the command path.** `Wire.*`, `MissionSession`, `Session.Fold`, the recorder, the reader, the replay, the dashboard, the fixture player and the test support modules do not reference the command subtree, and a compile-time boundary test enforces it; the HTTP endpoint serves no command route; when the flag is off the supervision tree is identical to M4's (an invariance test); recordings and replays remain equal with or without commands, because a command's effect reaches the observer only as ordinary engine-authored evidence.

## Consequences

- One more loopback port, one more flag per side, one more pre-flight item and one more ini variant in install and cleanup; the native gate's "engine writes: none" becomes "engine writes: only the registry's apply functions, listed by name".
- The first allowlist has two entries: `relay.probe` (no effect; the path validator) and one reversible semantic command whose engine mechanism and observability are established by the M5-C research (the M5 design's section 2.1); the preferred target is the player's outfit through `Functions::ZHitman5_SetOutfit`, observable through `disguise.equipped`, with the game-time multiplier as the documented fallback.
- Adding a command is a new allowlist entry with its own schema version, validator, preconditions, apply, read-back and reversal, reviewed on its own; the protocol version changes only for envelope-level changes.
- Staging: M5-A (BEAM boundary and protocol, offline, no native change) → M5-B (native acceptance and scheduling, offline gate) → M5-C (one reversible command, offline) → M5-D (one controlled runtime experiment with rollback). The smallest safe first authorization is M5-A.

## Alternatives rejected

- **Reusing the telemetry connection as a duplex channel**: couples command availability to the sink's drop-and-reconnect policy, puts command parsing on the telemetry sender thread, and reverses the sink's documented contract and the "listener never writes" tests; the observer would share a failure domain with the actor.
- **A native listening server** (as the Editor mod): a listening port inside the game process reachable by any local process, and the precedent of mutating engine state on the socket thread; contradicts ADR 0005.
- **Named pipes, file drops, an in-process NIF or port driver**: WSL2 interop complexity, unbounded polling state, or unsafe engine manipulation inside the BEAM (ARCHITECTURE's failure boundary).
- **A generic command (`call function`, `set property`, `signal pin by name`)**: exactly the capability the SDK's Editor exposes and the one M5 must not; it would make the allowlist meaningless and the reversal undefined.
- **Automatic retry or auto-revert**: both would act on an unconfirmed state; the design leaves retries and reversals to the operator with their own ladders.
